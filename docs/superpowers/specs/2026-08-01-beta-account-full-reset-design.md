# 21 天封測帳號完整重置設計

## 目標與範圍

在後台「會員管理」提供最高管理員專用的「重置 21 天封測帳號」功能。管理員可從 A、B399、B799 封測名單及符合舊版刪除復原條件的測試白名單帳號中選擇一人，將其恢復為尚未加入封測、尚未設定提醒、尚未簽到、尚未綁定守護人的全新狀態。

重置保留 LINE UID、付款訂單、交易／退款資料及不可修改的稽核／法務紀錄。重置後只能重新透過正確的 21 天封測流程取得資格；一般 LINE／LIFF 入口不得自動啟用 14 天體驗。正式部署後只進行唯讀驗證，不由部署流程實際重置任何正式會員。

## 現況問題

- `DEFAULT_PROFILE` 會建立 12:00、18:00 提醒且預設開啟，現有重置套用它後仍會顯示下次提醒。
- 首頁在伺服器確認前使用 `localStorage` 的簽到與提醒資料，重置後可能短暫或持續顯示舊狀態。
- 現有操作散落在會員列；已被刪除的測試帳號不再出現在會員資料中。
- 現有 `test_reset_pending` 會在一般入口重新註冊時建立 14 天體驗，與 21 天重新封測目的衝突。

## 採用方案

沿用目前單一持久狀態與 `mutate_state_atomically`，新增一個共用的完整重置服務、輕量測試帳號墓碑與 `account_state_version` 樂觀鎖。專用後台區塊及會員列按鈕都呼叫同一 API 與同一服務。

不採用只修正 `DEFAULT_PROFILE` 的局部方案，因為它無法處理反向關係、已刪除帳號、14 天誤啟用及前端舊快取。不另建獨立事件資料庫，因為目前專案仍以單一原子狀態儲存為主，跨儲存系統會增加不必要的一致性風險。

## 權限與候選資格

讀取候選資訊仍受管理員 session 保護。執行重置必須先通過 `_admin_guard(write=True, permission="member.manage")`，再確認目前角色為 `super_admin`。

LINE UID 必須在 `TEST_LINE_USER_IDS`，且符合下列任一規則：

1. 現有會員的 `beta_cohort` 為 `A`、`B399` 或 `B799`。
2. 測試帳號墓碑記錄該 UID 最後屬於 A、B399 或 B799，且尚未完成新版完整重置。
3. 白名單帳號曾被舊版永久刪除後由 LINE 自動建立；目前沒有 cohort、沒有正式付費權益、沒有 `beta_reset_pending`，列為「待重新封測」。

已完成新版完整重置、正式付費會員、非白名單帳號一律不列入。後端在寫入時重新計算候選資格，不能信任前端下拉內容。每次只處理一個帳號。

候選回應只提供顯示名稱、遮罩 UID、cohort／「待重新封測」、狀態、`account_state_version`，不包含付款明細或完整稽核內容。

## 資料模型

會員殼層新增／統一以下欄位：

- `beta_reset_pending: bool`：完整重置後為 `true`；一般入口不得清除。
- `beta_reset_origin_cohort: str`：只供後端重新指派判斷；A 組不可由公開 B 連結改配。
- `account_state_version: str`：每次完整重置產生不可預測的新版本。

全域新增 `test_account_tombstones`，以 LINE UID 為鍵。每筆只可包含：LINE UID、最後封測 cohort、顯示名稱、刪除／重置時間、狀態及必要版本資訊。不得包含簽到、提醒、守護、SOS、定位或付款內容。

稽核使用既有不可修改的管理員稽核集合，新增成功事件，記錄操作者、LINE UID、原 cohort、時間、保留範圍、清除摘要及新版本。原有稽核事件不得修改。

## 原子重置流程

API 請求包含 `confirm: true` 與管理員看到的 `account_state_version`。單一 `mutate_state_atomically` 回呼依序完成：

1. 重新驗證角色、白名單、候選條件、帳號存在／墓碑狀態及版本。
2. 深拷貝原狀態作為原子儲存失敗時的回滾基礎（由既有原子寫入機制負責）。
3. 保存顯示名稱、頭像及原 cohort；不搬動訂單、退款、交易、稽核、遷移稽核與法務紀錄。
4. 建立最小會員殼層：LINE UID、顯示名稱、頭像、`beta_reset_pending=true`、原 cohort、新 `account_state_version`；提醒時間為空陣列且每日提醒關閉。
5. 清除會員內的體驗／封測、方案權益、簽到、日曆、提醒、守護、聯絡人、群組、SOS、定位、安全守護、裝置互動與非稽核通知狀態。
6. 清除其他會員指向目標 UID 的 contacts、friends、guarding、invites、群組成員／管理員等反向關係。
7. 清除全域 guardian invites、beta members／feedback、SOS、location grants、guardian groups、rewards 及非稽核通知關聯。
8. 更新最小墓碑並寫入不可修改的成功稽核事件。

付款訂單與交易欄位不修改、不去識別化、不退款、不請款、不續訂。任何驗證或儲存失敗時整筆狀態維持重置前內容，也不得留下成功稽核事件。

## 重新登入與封測綁定

- 一般 LINE／LIFF 入口遇到 `beta_reset_pending=true` 時，只驗證 LINE 身分及更新可保留的顯示名稱／頭像，不建立 14 天體驗、不建立預設提醒、不恢復舊資料。
- B399／B799 封測連結可依連結重新建立新的 21 天期限及對應方案，成功後清除 `beta_reset_pending`。若原 cohort 是 A，公開 B 連結回傳衝突，不得誤配。
- A 組帳號只由既有最高管理員 A 組指派流程重新加入，成功後清除 pending。
- 新封測資格不繼承舊提醒、簽到、守護或群組資料。

## 前端快取規則

首頁在取得伺服器權威狀態前，不可根據本機資料顯示「今日已簽到」或下次提醒。等待時顯示「正在確認帳號狀態」；網路失敗顯示載入錯誤，不回退到舊簽到／提醒畫面。

方案摘要可快速顯示，但快取必須附帶 `account_state_version`。伺服器回傳版本與本機不同時，立即刪除該 LINE UID 的會員、今日簽到、守護提示及相關本機旗標，再完全依伺服器資料渲染。

## 後台介面

會員管理新增獨立區塊：

- 標題「重置 21 天封測帳號」。
- 候選下拉列出名稱、遮罩 UID、A／B399／B799 或「待重新封測」及目前狀態。
- 主要按鈕「重置選取帳號」。非 `super_admin` 只看得到說明與停用控制。
- 確認視窗明列保留與清除範圍；確認後按鈕停用並顯示「重置中…」。
- 成功後重新讀取會員與候選資料、移除已重置帳號，顯示「已重置，可重新使用 21 天封測連結綁定」。
- 無候選時顯示「目前沒有可重置的 21 天封測測試帳號」。

會員列的「重設測試帳號」改呼叫同一 API，文案改為可重新封測。永久刪除保留，但明確標示為永久刪除會員資料，避免混淆。

## API 與錯誤

建議提供：

- `GET /api/admin/beta-reset-candidates`：回傳安全候選摘要與權限狀態。
- `POST /api/admin/test-accounts/<line_user_id>/reset`：沿用路徑，升級為完整重置語意。

錯誤契約：

- 非最高管理員：403，「只有最高管理員可以重置封測帳號」。
- 非白名單或不符合候選規則：403，不修改資料。
- 帳號不存在：404；已完成重置或目前不可重置：409。
- 候選版本不一致：409，「帳號資料已變更，請重新載入後再確認」。
- 儲存失敗：500，原子回滾，不產生成功稽核。

## 測試與正式驗收

採 TDD，先建立會失敗的後端與前端測試，再做最小實作。至少驗證：候選篩選、角色與白名單限制、保留 UID／訂單／稽核、所有正反向與全域資料歸零、空提醒與關閉狀態、一般入口不開 14 天、正確連結重建 21 天、A 組限制、版本衝突、舊快取清除、專用後台操作狀態及原子回滾。

部署前執行完整 Python 與 Node 行為測試及語法檢查。部署後只做健康端點、公開頁載入及後台區塊可見性的唯讀檢查；不替管理員按下任何正式帳號的重置按鈕。
