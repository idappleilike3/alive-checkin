# 每日平安第二段設計：後台上鎖、準時排程與 SOS 入口統一

日期：2026-07-26  
狀態：已由產品負責人同意開始執行，實作前書面確認版

## 1. 目標與範圍

本段只處理三個可獨立驗收的問題：

1. 關閉公開後台，改成安全登入與工作階段驗證。
2. 移除依賴網站程序的背景執行緒，改用一個 Render Cron Job 準時觸發所有排程。
3. 將 LINE 圖文選單、LINE 關鍵字與 LIFF 內的「需要幫忙／SOS」導向同一個三次確認畫面。

本段不包含核心守護人綁定重整、持續定位、藍新正式交易與會員中心改版；這些另開後續規格，以免一次修改過多重要流程。

## 2. 後台上鎖

### 2.1 使用方式

- `/admin.html` 可開啟登入畫面，但登入前不得取得任何會員、訂單、通知或守護人資料。
- 管理者輸入密碼後，前端呼叫 `POST /api/admin/login`。
- 密碼只放在 HTTPS request body，不再出現在網址、瀏覽器紀錄、伺服器 access log 或書籤中。
- 登入成功後建立 8 小時工作階段；瀏覽器使用 `HttpOnly`、`Secure`、`SameSite=Strict` Cookie。
- 後台 API 一律檢查工作階段；未登入回傳 HTTP 401，前端立即回到登入畫面。
- 提供登出按鈕，呼叫 `POST /api/admin/logout` 並清除工作階段。

### 2.2 安全設定

- `ALLOW_OPEN_ADMIN` 與 `ADMIN_OPEN` 不再能讓正式環境免密碼開放。
- `ADMIN_PASSWORD` 空白時採 fail closed：後台 API 回傳 503「後台尚未完成安全設定」，不可自動開放。
- 新增 `ADMIN_SESSION_SECRET`，只存在 Render Environment，不寫入 Git。
- 登入失敗採短時間速率限制；不在回應中透露密碼是否接近正確。
- 寫入型後台 API 需同時驗證工作階段與 CSRF token。
- 保留舊的密碼驗證函式只供過渡測試，正式路由不再接受 `?password=`。
- 登入、登出、修改方案、指定核心守護人、人工推播、備份與圖文選單部署都寫入後台稽核紀錄；不記錄密碼、token 或完整個資。

### 2.3 相容性

- Flask 正式服務走工作階段驗證。
- 內建 fallback server 不承載正式後台；若無法安全支援 session，後台 API 採關閉，不降級成公開模式。

## 3. 準時排程與成本控制

### 3.1 架構

- 關閉 `_start_internal_scheduler()`，Web service 不再自行開背景執行緒。
- 新增單一 `POST /api/cron/tick` 入口，由既有 `CRON_SECRET` 驗證。
- `tick` 每次依台北時間執行：
  - 每日報平安提醒
  - 逾期未報平安通知
  - 生日提醒
  - 智慧提醒
  - 到期／續費提醒
  - 聯絡資料提醒
  - 守護群人數刷新
  - 到期 SOS 與必要資料清理
- `render.yaml` 只保留一個共用 Cron Job，每 5 分鐘呼叫一次 `/api/cron/tick`。
- 既有細分 cron API 暫時保留，方便管理者手動重跑與相容舊設定，但 Render Blueprint 不再建立六個付費 Cron Job。

### 3.2 準時定義

- 使用者設定的提醒時間以 `Asia/Taipei` 判定。
- 一般提醒的允許送達範圍為設定時間後 0–4 分鐘，符合共用 cron 的五分鐘粒度。
- 不再因 Web service 下午醒來而補送早上的舊提醒。
- 若 Render 或 LINE 在時間窗內持續故障，該次記錄為未送達，不在數小時後打擾使用者；後台顯示原因供人工處理。
- 每項排程使用穩定的冪等鍵，例如「功能＋LINE 使用者＋台北日期＋時段」，同一時段最多成功發送一次。

### 3.3 LINE 錯誤分類

- HTTP 400 且 LINE 回覆目標無效：標記為永久失敗／需重新加好友，不再每五分鐘重送。
- HTTP 401／403：標記系統設定錯誤並停止該輪推播，後台顯示 LINE token／權限需處理。
- HTTP 429：依 `Retry-After` 或下一輪排程重試，設定當日重試上限。
- HTTP 5xx、timeout、網路錯誤：視為暫時失敗，以有限次數重試。
- 成功、永久失敗、暫時失敗都寫入可讀的通知紀錄，避免同一錯誤洗滿後台。

## 4. SOS 入口統一

### 4.1 單一入口

- 唯一正式入口為 LIFF：`https://liff.line.me/2010674803-rK98c0lo/?open=sos`。
- LINE 圖文選單「需要幫忙」改為 URI action，直接開啟這個入口。
- LIFF 首頁的 SOS 浮動按鈕與安全守護頁的 SOS 按鈕呼叫同一個 `openSosFlow()`。
- 使用者在聊天室輸入「需要幫忙」「SOS」「緊急求助」時，Bot 回覆同一張入口卡，卡片主按鈕也開啟同一個 LIFF SOS 畫面。
- 不再同時維護一套聊天室 postback 三次確認和一套 LIFF 三次確認。

### 4.2 三次確認與定位

- 畫面清楚顯示「連按 3 次才會通知核心守護人」，每按一次即顯示 `1/3`、`2/3`、`3/3`。
- 第一次按下時就開始請求定位，避免第三次才開始等待。
- 第三次按下後最多等到第一次按下起算 8 秒；取得定位就附上 Google Maps 連結、座標時間與最後更新時間。
- 定位被拒或逾時時，SOS 仍需送出，畫面明確告知「已通知，但未附即時位置」。
- 若沒有任何可通知的核心守護人，不顯示成功；改顯示「尚未設定可通知的核心守護人」，並提供撥打 119、110 與緊急聯絡人的按鈕。
- LINE 推播失敗時，前端顯示實際通知成功人數與可理解原因，不再只顯示「已通知 0 位」。

### 4.3 成功結果

- 成功畫面顯示：
  - 已通知幾位核心守護人
  - 是否附上位置
  - 發送時間
  - 可取消狀態（若既有產品規則仍允許取消）
- 後端仍保留每日次數上限與冷卻時間，避免誤觸與濫用。

## 5. 資料流

### 後台

`登入表單 → /api/admin/login → 建立安全 session + CSRF → 後台 API → 稽核紀錄`

### 排程

`Render 單一 Cron → /api/cron/tick → 台北時間判定 → 各排程函式 → 冪等與錯誤分類 → LINE → 通知紀錄`

### SOS

`圖文選單／首頁／聊天室入口卡 → 同一 LIFF SOS 畫面 → 三次確認 + 定位請求 → /api/sos → 核心守護人 LINE 推播 → 結果畫面`

## 6. 測試與驗收

### 自動測試

- 未設定密碼時，所有後台資料 API 都拒絕存取。
- 正確登入可建立 session；錯誤密碼、過期 session、無 CSRF 的寫入請求均被拒絕。
- 網址與前端 fetch 不再含 `password=`。
- `tick` 在同一時段重跑不重複推播。
- 過期數小時的提醒不補送。
- LINE 400 永久失敗不重試；429／5xx 依規則有限重試。
- Render Blueprint 只宣告一個 cron service，且正式環境關閉 internal scheduler。
- 圖文選單「需要幫忙」為 LIFF URI action。
- 三個 LIFF SOS 按鈕共用同一流程。
- SOS 有定位、無定位、無核心守護人、部分成功與全數失敗都有測試。

### 上線驗收

1. 未登入開啟 `/admin.html` 看不到資料。
2. 登入後可查看後台，登出後舊頁面立即失效。
3. 建立一個五分鐘後的提醒，確認於設定時間後 0–4 分鐘收到。
4. 同一提醒不會重複發送。
5. 從圖文選單與 LIFF 首頁進入時，看到相同 SOS 畫面。
6. 測試帳號連按三次後，核心守護人收到地圖連結；拒絕定位時仍收到不含位置的通知。
7. 無可通知核心守護人時，畫面不會誤報成功。

## 7. 部署順序與回復方式

1. 先部署程式，但保持新 cron 尚未啟用。
2. 在 Render 設定強密碼、`ADMIN_SESSION_SECRET`、`CRON_SECRET`，並確認 `ALLOW_OPEN_ADMIN=false`。
3. 驗證後台登入與既有管理功能。
4. 建立單一共用 Cron Job，確認 `/api/cron/tick` 成功。
5. 關閉舊 cron services 與 internal scheduler。
6. 更新並重新部署 LINE 圖文選單。
7. 完成測試帳號 SOS 與提醒驗收後再開放正式使用。

若排程異常，可暫時停用新的共用 Cron 並回到舊細分 cron 端點；不可重新開啟公開後台。
